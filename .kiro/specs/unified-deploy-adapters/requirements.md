# Requirements Document

## Introduction

The deploy pipeline currently has two completely separate code paths for AWS and GCP, with duplicated logic split across the `deploy` and `image-builder` services. The `deploy/repo-analyzer/` module generates Dockerfiles for GCP deploys, while `image-builder/detection/` generates different Dockerfiles for the same frameworks for AWS deploys. These two generators produce materially different outputs — for example, the deploy service's PHP generator uses `php artisan serve` on a `php:X.Y-cli` base image, while the image-builder's PHP generator uses `php-fpm + nginx + supervisor` on a `php:X.Y-fpm` base image (the production-ready approach).

Infrastructure provisioning is also fragmented: GCP VPS uses Pulumi with bash user-data scripts, GCP managed uses Pulumi Cloud Run resources, AWS EC2 uses CloudFormation with cfn-init, and AWS ECS uses CloudFormation with Fargate resources. Environment variable forwarding differs per provider — GCP uses placeholder replacement in Pulumi scripts, while AWS chains SNS → CodeBuild → Lambda → CloudFormation parameters → bash scripts.

This refactor introduces a **Unified Deploy Processor** with a **Provider Adapter** pattern. A single orchestrator handles the common pipeline (clone → detect → generate Dockerfile → build image), then dispatches to a provider-specific adapter that implements a common interface for pushing images, provisioning infrastructure, injecting environment variables, and running post-deploy commands. Adding a new cloud provider requires only a new adapter file plus registration in the adapter registry.

## Glossary

- **Deploy_Processor**: The unified orchestrator module (`deploy/processor/index.ts`) that executes the common deploy pipeline steps and dispatches to the appropriate Provider_Adapter.
- **Provider_Adapter**: A module implementing the `DeployAdapter` interface for a specific cloud provider and deploy target combination (e.g., `aws-ecs`, `gcp-cloudrun`, `gcp-compute`, `aws-ec2`, `aws-s3`, `gcp-storage`).
- **Adapter_Registry**: A lookup table mapping provider + deploy strategy combinations to their corresponding Provider_Adapter implementation.
- **Stack_Detector**: The single, consolidated module responsible for detecting the runtime, framework, package manager, and project structure of a cloned repository.
- **Dockerfile_Generator**: The single, consolidated module responsible for generating production-ready Dockerfiles for each supported runtime (Node.js, PHP, Python, Go).
- **DeployAdapter_Interface**: The TypeScript interface that all Provider_Adapters implement, defining methods for `pushImage`, `provisionInfrastructure`, `injectEnvVars`, and `runPostDeploy`.
- **Image_Builder_Service**: The existing `image-builder/` Encore service that provides a direct API for building Docker images via AWS CodeBuild. Retained for its standalone API but no longer called by the Deploy_Processor during standard deploys.
- **Deploy_Service**: The existing `deploy/` Encore service that orchestrates deployments via pub/sub.
- **Repo_Analyzer**: The existing `deploy/repo-analyzer/` module that detects project configuration and generates Dockerfiles for the deploy service.
- **Detection_Module**: The existing `image-builder/detection/` module that detects project stacks and generates Dockerfiles for the image-builder service.
- **Pulumi_Template**: A TypeScript program generated by the deploy service that defines cloud infrastructure using the Pulumi SDK (used for GCP deploys and AWS ECS via `@pulumi/docker`).
- **CloudFormation_Template**: A YAML template defining AWS infrastructure resources (used for AWS ECS Fargate, EC2, and S3 deploys via the image-builder pipeline).
- **Deploy_Target**: The specific infrastructure target for a deployment: `ecs` (AWS ECS Fargate), `ec2` (AWS EC2 single instance), `s3` (AWS S3 + CloudFront static site), `cloudrun` (GCP Cloud Run), `compute` (GCP Compute Engine VPS), or `storage` (GCP Cloud Storage + CDN).

## Requirements

### Requirement 1: Unified Stack Detection Module

**User Story:** As a developer, I want a single stack detection module used by all deploy paths, so that framework detection is consistent regardless of which cloud provider I deploy to.

#### Acceptance Criteria

1. THE Stack_Detector SHALL detect the following runtimes: Node.js, PHP, Python, and Go.
2. WHEN a Node.js project is detected, THE Stack_Detector SHALL identify the framework (Next.js, Nuxt, SvelteKit, Angular, Astro, SPA, or generic), the package manager (npm, pnpm, yarn, or bun), whether Next.js standalone output is configured, and whether the project is a static export.
3. WHEN a PHP project is detected, THE Stack_Detector SHALL identify whether the project uses Laravel, detect required PHP extensions from `composer.json` and `composer.lock`, and detect whether frontend assets require a Node.js build step.
4. WHEN a Python project is detected, THE Stack_Detector SHALL identify the framework (Django, FastAPI, Flask, or generic).
5. WHEN a Go project is detected, THE Stack_Detector SHALL read the Go version from `go.mod`.
6. WHEN a monorepo or subdirectory project is detected, THE Stack_Detector SHALL identify the application subdirectory and scope detection to that subdirectory.
7. THE Stack_Detector SHALL produce a single `DetectedStack` type that contains all information needed by both the Dockerfile_Generator and the Provider_Adapters.
8. THE Stack_Detector SHALL consolidate the logic currently in `deploy/repo-analyzer/` (analyzers and `detect-subdir.ts`) and `image-builder/detection/` (detectors and `helpers.ts`) into one module.
9. THE Stack_Detector SHALL be located in `deploy/repo-analyzer/` and the `image-builder/detection/` module SHALL import from it rather than maintaining a separate implementation.

### Requirement 2: Unified Dockerfile Generator

**User Story:** As a developer, I want a single Dockerfile generator per runtime, so that I get the same production-ready Dockerfile regardless of which provider I deploy to.

#### Acceptance Criteria

1. THE Dockerfile_Generator SHALL produce one Dockerfile per runtime (Node.js, PHP, Python, Go) that is used by all deploy paths.
2. WHEN generating a PHP Laravel Dockerfile, THE Dockerfile_Generator SHALL use the `php:X.Y-fpm-{debian}` base image with nginx and supervisord (the image-builder pattern), not the `php:X.Y-cli` base image with `php artisan serve` (the deploy service pattern).
3. WHEN generating a PHP Laravel Dockerfile, THE Dockerfile_Generator SHALL include a multi-stage build with stages for base, deps, frontend (when Node assets are present), and runner.
4. WHEN generating a PHP Laravel Dockerfile, THE Dockerfile_Generator SHALL configure storage permissions, `.env` generation, `artisan key:generate`, and cache clearing in the runner stage.
5. WHEN generating a PHP Laravel Dockerfile, THE Dockerfile_Generator SHALL detect required PHP extensions from `composer.json` and `composer.lock` and install them, including PECL extensions (redis, imagick, etc.) and version-specific handling (e.g., `imap` via PECL on PHP 8.4+).
6. WHEN generating a Node.js Dockerfile, THE Dockerfile_Generator SHALL detect the Node.js version from `.nvmrc`, `.node-version`, or `package.json` engines field, and use the correct package manager install and build commands.
7. WHEN generating a Node.js Dockerfile, THE Dockerfile_Generator SHALL handle framework-specific output structures: Next.js standalone, Next.js standard, Nuxt (SSR and static), SvelteKit with adapter-node, Angular, SPA (Vite/React/Vue), and Astro (SSR and static).
8. WHEN generating a Python Dockerfile, THE Dockerfile_Generator SHALL detect the framework and use the appropriate production server (gunicorn for Django/Flask, uvicorn for FastAPI).
9. WHEN generating a Go Dockerfile, THE Dockerfile_Generator SHALL use a multi-stage build with an Alpine builder and a minimal Alpine production image.
10. THE Dockerfile_Generator SHALL be located in `deploy/repo-analyzer/dockerfiles/` and the `image-builder/` service SHALL import from it rather than maintaining separate generators.
11. WHEN a repository already contains a user-provided Dockerfile, THE Dockerfile_Generator SHALL preserve the user-provided Dockerfile and skip generation.

### Requirement 3: Provider Adapter Interface

**User Story:** As a platform maintainer, I want a common interface for all provider adapters, so that adding a new cloud provider requires only implementing the interface and registering the adapter.

#### Acceptance Criteria

1. THE DeployAdapter_Interface SHALL define the following methods: `pushImage(params)`, `provisionInfrastructure(params)`, `injectEnvVars(params)`, and `runPostDeploy(params)`.
2. THE DeployAdapter_Interface SHALL define a `supports(provider, deployStrategy)` method that returns whether the adapter handles a given provider and deploy strategy combination.
3. THE DeployAdapter_Interface SHALL define return types that include the provisioned application URL, resource identifiers, and status information.
4. THE DeployAdapter_Interface SHALL accept a common `AdapterContext` parameter containing the deployment ID, repository name, detected stack, built image reference, environment variables, provider credentials, region, and deploy event metadata.
5. THE DeployAdapter_Interface SHALL be defined as a TypeScript interface in `deploy/processor/adapters/types.ts`.

### Requirement 4: Adapter Registry

**User Story:** As a platform maintainer, I want a registry that maps provider and deploy strategy combinations to adapters, so that the Deploy_Processor can dispatch to the correct adapter without conditional branching.

#### Acceptance Criteria

1. THE Adapter_Registry SHALL map each combination of provider (`aws`, `gcp`) and deploy strategy (`vps`, `managed`, `static`) to a specific Provider_Adapter.
2. WHEN a deployment event is received, THE Deploy_Processor SHALL look up the correct Provider_Adapter from the Adapter_Registry using the provider and deploy strategy from the event.
3. IF no Provider_Adapter is registered for a given provider and deploy strategy combination, THEN THE Deploy_Processor SHALL fail the deployment with a descriptive error message identifying the unsupported combination.
4. THE Adapter_Registry SHALL allow new adapters to be registered by adding a single entry, without modifying the Deploy_Processor orchestration logic.
5. THE Adapter_Registry SHALL be located in `deploy/processor/adapters/index.ts`.

### Requirement 5: GCP Cloud Run Adapter

**User Story:** As a developer deploying to GCP Cloud Run, I want the unified pipeline to handle my deployment end-to-end, so that I get the same result as the current GCP managed deploy path.

#### Acceptance Criteria

1. WHEN a GCP Cloud Run deployment is requested, THE GCP_CloudRun_Adapter SHALL push the Docker image to GCP Artifact Registry using an OAuth2 access token derived from the service account key.
2. WHEN a GCP Cloud Run deployment is requested, THE GCP_CloudRun_Adapter SHALL enable the `artifactregistry.googleapis.com` and `run.googleapis.com` APIs on the GCP project.
3. WHEN a GCP Cloud Run deployment is requested, THE GCP_CloudRun_Adapter SHALL create the Artifact Registry repository if it does not exist.
4. WHEN a GCP Cloud Run deployment is requested, THE GCP_CloudRun_Adapter SHALL provision infrastructure using the existing Pulumi Cloud Run template (`deploy/pulumi-templates/gcp.ts` `buildGcpCloudRun`).
5. WHEN a previous Pulumi state exists for the same repo, provider, and deploy strategy, THE GCP_CloudRun_Adapter SHALL restore the state before running `pulumi up`.
6. WHEN a Cloud Run service already exists but no Pulumi state is available, THE GCP_CloudRun_Adapter SHALL inject Pulumi import directives to adopt the existing resource.
7. THE GCP_CloudRun_Adapter SHALL inject user-provided environment variables into the Pulumi program before execution.
8. THE GCP_CloudRun_Adapter SHALL be located in `deploy/processor/adapters/gcp-cloudrun.ts`.

### Requirement 6: GCP Compute Engine Adapter

**User Story:** As a developer deploying to a GCP VPS, I want the unified pipeline to handle my deployment end-to-end, so that I get the same result as the current GCP VPS deploy path.

#### Acceptance Criteria

1. WHEN a GCP Compute Engine deployment is requested, THE GCP_Compute_Adapter SHALL push the Docker image to GCP Artifact Registry.
2. WHEN a GCP Compute Engine deployment is requested, THE GCP_Compute_Adapter SHALL enable the `artifactregistry.googleapis.com` and `compute.googleapis.com` APIs on the GCP project.
3. WHEN a GCP Compute Engine deployment is requested, THE GCP_Compute_Adapter SHALL provision infrastructure using the existing Pulumi Compute Engine template (`deploy/pulumi-templates/gcp.ts` `buildGcpComputeEngine`).
4. WHEN the Pulumi provisioning completes and a server IP is available, THE GCP_Compute_Adapter SHALL transfer the Docker image to the server via SCP and start the container with the correct port mapping and environment variables.
5. WHEN a user SSH key is configured, THE GCP_Compute_Adapter SHALL combine the user SSH key with a deploy-specific SSH key for server access.
6. THE GCP_Compute_Adapter SHALL replace placeholder tokens (`__AR_IMAGE_URI__`, `__AR_TOKEN__`, `__USER_ENV_FLAGS__`, `__DEPLOY_DB_NAME__`, `__DEPLOY_DB_USER__`, `__DEPLOY_DB_PASS__`) in the Pulumi program before execution.
7. THE GCP_Compute_Adapter SHALL be located in `deploy/processor/adapters/gcp-compute.ts`.

### Requirement 7: GCP Cloud Storage + CDN Adapter

**User Story:** As a developer deploying a static site to GCP, I want the unified pipeline to handle my deployment end-to-end, so that I get the same result as the current GCP static deploy path.

#### Acceptance Criteria

1. WHEN a GCP static site deployment is requested, THE GCP_Storage_Adapter SHALL skip Docker image building entirely.
2. WHEN a GCP static site deployment is requested, THE GCP_Storage_Adapter SHALL enable the `compute.googleapis.com` API on the GCP project.
3. WHEN a GCP static site deployment is requested, THE GCP_Storage_Adapter SHALL provision infrastructure using the existing Pulumi Cloud Storage + CDN template (`deploy/pulumi-templates/gcp.ts` `buildGcpCloudStorageCdn`).
4. WHEN the Pulumi provisioning completes, THE GCP_Storage_Adapter SHALL build the static site locally (using the detected package manager), identify the output directory, and upload the files to the GCS bucket.
5. THE GCP_Storage_Adapter SHALL be located in `deploy/processor/adapters/gcp-storage.ts`.

### Requirement 8: AWS ECS Fargate Adapter

**User Story:** As a developer deploying to AWS ECS, I want the unified pipeline to build the Docker image locally and push it to ECR, so that the deploy service handles the full pipeline without depending on the image-builder service.

#### Acceptance Criteria

1. WHEN an AWS ECS deployment is requested, THE AWS_ECS_Adapter SHALL build the Docker image locally using the unified Dockerfile_Generator output.
2. WHEN an AWS ECS deployment is requested, THE AWS_ECS_Adapter SHALL push the Docker image to AWS ECR, creating the ECR repository if it does not exist.
3. WHEN an AWS ECS deployment is requested, THE AWS_ECS_Adapter SHALL provision infrastructure using CloudFormation with the existing `image-builder/deploy-templates/ecs-fargate.yml` template.
4. WHEN user-provided environment variables are present, THE AWS_ECS_Adapter SHALL inject them into the ECS task definition container environment.
5. THE AWS_ECS_Adapter SHALL poll CloudFormation stack status until the deployment completes or fails, logging progress to the deployment record.
6. WHEN the CloudFormation stack reaches `CREATE_COMPLETE` or `UPDATE_COMPLETE`, THE AWS_ECS_Adapter SHALL extract the application URL from the stack outputs.
7. IF the CloudFormation stack is in `ROLLBACK_COMPLETE` or `ROLLBACK_FAILED` state from a previous deployment, THEN THE AWS_ECS_Adapter SHALL delete the stack and recreate it.
8. THE AWS_ECS_Adapter SHALL be located in `deploy/processor/adapters/aws-ecs.ts`.

### Requirement 9: AWS EC2 Adapter

**User Story:** As a developer deploying to an AWS EC2 instance, I want the unified pipeline to handle my deployment end-to-end, so that I get the same result as the current AWS EC2 deploy path.

#### Acceptance Criteria

1. WHEN an AWS EC2 deployment is requested, THE AWS_EC2_Adapter SHALL build the Docker image locally and push it to AWS ECR.
2. WHEN an AWS EC2 deployment is requested, THE AWS_EC2_Adapter SHALL provision infrastructure using CloudFormation with the existing `image-builder/deploy-templates/ec2.yml` template.
3. WHEN user-provided environment variables are present, THE AWS_EC2_Adapter SHALL pass them as the `EnvVarsJson` CloudFormation parameter.
4. WHEN self-hosted services (database, cache, queue) are requested, THE AWS_EC2_Adapter SHALL pass them as the `SelfHostedServices` CloudFormation parameter.
5. WHEN tech stack identifiers are present, THE AWS_EC2_Adapter SHALL pass them as the `TechStack` CloudFormation parameter for framework-specific post-deploy setup (e.g., Laravel migrations, queue workers, scheduler cron).
6. THE AWS_EC2_Adapter SHALL be located in `deploy/processor/adapters/aws-ec2.ts`.

### Requirement 10: AWS S3 + CloudFront Adapter

**User Story:** As a developer deploying a static site to AWS, I want the unified pipeline to handle my deployment end-to-end, so that I get the same result as the current AWS S3 deploy path.

#### Acceptance Criteria

1. WHEN an AWS S3 static site deployment is requested, THE AWS_S3_Adapter SHALL skip Docker image building entirely.
2. WHEN an AWS S3 static site deployment is requested, THE AWS_S3_Adapter SHALL build the static site locally, upload the output to an S3 bucket, and provision a CloudFront distribution using the existing `image-builder/deploy-templates/s3.yml` CloudFormation template.
3. THE AWS_S3_Adapter SHALL be located in `deploy/processor/adapters/aws-s3.ts`.

### Requirement 11: Unified Deploy Processor Orchestration

**User Story:** As a platform maintainer, I want the Deploy_Processor to follow a single orchestration flow for all providers, so that the deploy pipeline is maintainable and predictable.

#### Acceptance Criteria

1. THE Deploy_Processor SHALL execute the following steps in order for every deployment: (a) clone repository, (b) detect stack using the unified Stack_Detector, (c) generate Dockerfile using the unified Dockerfile_Generator (unless the deploy target is static or the repo has a user-provided Dockerfile), (d) look up the Provider_Adapter from the Adapter_Registry, (e) delegate to the Provider_Adapter.
2. THE Deploy_Processor SHALL pass the detected stack, generated Dockerfile path, cloned repository path, environment variables, provider credentials, and deploy event metadata to the Provider_Adapter.
3. THE Deploy_Processor SHALL log each pipeline step (clone, detect, generate, build, push, provision) to the deployment record using the existing `appendLog` helper.
4. IF any pipeline step fails, THEN THE Deploy_Processor SHALL update the deployment status to `failed` and log the error message.
5. THE Deploy_Processor SHALL continue to handle template deploys (e.g., WordPress) through the existing `handleTemplateDeploy` path, bypassing the unified pipeline for template deployments.
6. WHEN the Deploy_Processor receives a deployment event, THE Deploy_Processor SHALL determine the provider and deploy strategy from the event and provider record, then dispatch to the correct adapter without provider-specific conditional logic in the orchestrator.

### Requirement 12: Image Builder Service Independence

**User Story:** As a frontend developer, I want the image-builder service to continue providing its direct build API, so that I can trigger builds independently of the deploy pipeline.

#### Acceptance Criteria

1. THE Image_Builder_Service SHALL continue to expose its existing API endpoints (`/image-builder/builds`, `/image-builder/builds/:buildId`, `/image-builder/builds/:buildId/logs`, `/image-builder/builds/:buildId/cancel`).
2. THE Image_Builder_Service SHALL import the unified Stack_Detector and Dockerfile_Generator from `deploy/repo-analyzer/` instead of maintaining its own `detection/` module.
3. THE Deploy_Processor SHALL NOT call the Image_Builder_Service during the standard deploy flow — the Deploy_Processor SHALL build and push images directly through the Provider_Adapter.
4. THE Image_Builder_Service SHALL continue to use AWS CodeBuild for its direct API builds, as CodeBuild provides build isolation and logging that the direct API requires.

### Requirement 13: Backward Compatibility

**User Story:** As an existing user, I want all my current deployments to continue working after the refactor, so that the migration is transparent.

#### Acceptance Criteria

1. THE unified pipeline SHALL support all six existing Deploy_Targets: GCP Cloud Run, GCP Compute Engine, GCP Cloud Storage + CDN, AWS ECS Fargate, AWS EC2, and AWS S3 + CloudFront.
2. THE unified pipeline SHALL preserve the existing deployment database schema — the `deployments` table columns (`status`, `logs`, `app_url`, `commit_hash`, `docker_image`, `deploy_strategy`) SHALL remain unchanged.
3. THE unified pipeline SHALL preserve the existing pub/sub contract — the `DeployEvent` interface SHALL remain backward-compatible.
4. THE unified pipeline SHALL preserve the existing Pulumi templates for GCP (`deploy/pulumi-templates/gcp.ts`) and the existing CloudFormation templates for AWS (`image-builder/deploy-templates/`).
5. THE unified pipeline SHALL preserve the existing Pulumi state persistence mechanism (state embedded in `tofu_script` column, restored on subsequent deploys).
6. WHEN a deployment uses the `buildMethod` field set to `codebuild`, THE Deploy_Processor SHALL route to the AWS adapter path that uses CodeBuild (for backward compatibility with in-flight deployments during migration).
7. THE unified pipeline SHALL preserve template deploy support (e.g., WordPress) through the existing `handleTemplateDeploy` path.

### Requirement 14: Dockerfile Auto-Patching

**User Story:** As a developer, I want the deploy pipeline to automatically fix common Dockerfile build failures, so that my deployments succeed without manual intervention.

#### Acceptance Criteria

1. WHEN a Docker build fails, THE Deploy_Processor SHALL invoke the existing `patchDockerfile` function to attempt an automatic fix.
2. THE Deploy_Processor SHALL retry the Docker build up to 3 times, applying auto-patches between attempts.
3. IF all 3 build attempts fail, THEN THE Deploy_Processor SHALL report the failure with the last build error output.

### Requirement 15: Environment Variable Injection

**User Story:** As a developer, I want environment variables I configure in the deploy wizard to be correctly forwarded to my running application, regardless of which provider I deploy to.

#### Acceptance Criteria

1. WHEN user-provided environment variables are present, THE Provider_Adapter SHALL inject them into the running application through the provider-appropriate mechanism (Pulumi config for GCP, CloudFormation parameters for AWS, `docker run -e` flags for VPS deploys).
2. WHEN infrastructure services are provisioned (database, cache), THE Provider_Adapter SHALL inject infrastructure connection environment variables (e.g., `DB_HOST`, `REDIS_HOST`) that override user-provided values to ensure correct connectivity.
3. THE Provider_Adapter SHALL ensure that infrastructure override environment variables (e.g., `DB_HOST=host.docker.internal` for VPS deploys) take precedence over user-provided values for the same variable name.

### Requirement 16: New Provider Extensibility

**User Story:** As a platform maintainer, I want to add a new cloud provider by creating a single adapter file and registering it, so that the deploy pipeline is easy to extend.

#### Acceptance Criteria

1. WHEN a new cloud provider is added, THE platform maintainer SHALL create a new adapter file in `deploy/processor/adapters/` that implements the DeployAdapter_Interface.
2. WHEN a new cloud provider is added, THE platform maintainer SHALL register the adapter in the Adapter_Registry (`deploy/processor/adapters/index.ts`).
3. THE Deploy_Processor orchestration logic SHALL NOT require modification when a new provider adapter is registered.
4. THE existing provider registration steps (adding to `DeployProvider` type, `SUPPORTED_PROVIDERS`, Pulumi templates, default regions, resource estimators, URL generators) SHALL remain applicable for providers that use Pulumi for infrastructure provisioning.

### Requirement 17: Docker Image Caching

**User Story:** As a developer redeploying the same commit, I want the pipeline to reuse a previously built Docker image, so that redeployments are faster.

#### Acceptance Criteria

1. WHEN a deployment is for the same repository, branch, and commit hash as a previous successful deployment, THE Deploy_Processor SHALL check whether the previously built Docker image is still available locally.
2. WHEN a cached Docker image is available locally, THE Deploy_Processor SHALL skip the Docker build step and reuse the cached image.
3. WHEN a cached Docker image is not available locally, THE Deploy_Processor SHALL perform a full Docker build.

### Requirement 18: Deployment Status Tracking

**User Story:** As a developer, I want to see the status of my deployment progress through each pipeline stage, so that I can understand where the deployment is and diagnose failures.

#### Acceptance Criteria

1. THE Deploy_Processor SHALL update the deployment status through the following stages: `pending` → `building` → `deploying` → `success` or `failed`.
2. THE Deploy_Processor SHALL log timestamped messages for each pipeline step: repository clone, stack detection result, Dockerfile generation, Docker build progress, image push, infrastructure provisioning, and completion.
3. WHEN a deployment fails, THE Deploy_Processor SHALL log the last 20 lines of error output from the failed step.
4. WHEN a deployment succeeds, THE Deploy_Processor SHALL update the `app_url` column with the application URL extracted from the provider's infrastructure outputs.
